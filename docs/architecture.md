# Архитектура

`mvc-v1` — учебное серверное PHP-приложение с небольшим собственным MVC-ядром. Архитектура намеренно остаётся прямой: маршрутизатор выбирает сценарий, контроллер координирует запрос, модель работает с данными, представление формирует страницу, а готовый HTTP-ответ отправляется в одной точке.

Проект не задуман как универсальный фреймворк и не пытается воспроизводить полный набор возможностей Symfony, Laravel или других промышленных решений.

## Общий поток запроса

```text
HTTP-запрос
    ↓
Router
    ↓
Track
    ↓
Dispatcher
    ↓
метод контроллера
    ↓
Page | Response
    ↓
Page → View → Response
    ↓
public/index.php
    ↓
код состояния + заголовки + тело
```

Входной скрипт [`public/index.php`](../public/index.php) загружает конфигурацию и маршруты, нормализует URI, получает `Track` от `Router` и передаёт его в `Dispatcher`.

Если контроллер возвращает `Page`, она передаётся в `View` для формирования HTML. Если контроллер уже вернул `Response` или `RedirectResponse`, представление не вызывается. В обоих случаях входной скрипт получает готовый `Response` и только после этого отправляет код состояния, заголовки и тело ответа.

## Router и Track

[`Router`](../core/src/Router.php) сопоставляет путь запроса с маршрутами из [`config/routes.php`](../config/routes.php).

При разборе URI:

- параметры после `?` не участвуют в выборе маршрута;
- именованные сегменты маршрута превращаются в параметры;
- имя контроллера, имя метода и параметры упаковываются в `Track`;
- если маршрут не найден, создаётся `Track` для `ErrorController::notFound()`.

`Router` не создаёт контроллеры и ничего не отправляет клиенту самостоятельно.

## Dispatcher

[`Dispatcher`](../core/src/Dispatcher.php) отвечает за переход от `Track` к нужному методу контроллера.

Он:

1. проверяет допустимый формат имени контроллера и метода;
2. проверяет `APP_NAMESPACE`;
3. подключает файл контроллера;
4. убеждается, что класс и метод существуют и доступны;
5. вызывает метод с параметрами маршрута;
6. принимает только `Page` или `Response`.

Штатный HTTP-результат не выражается исключением. Контроллер возвращает страницу, обычный ответ или `RedirectResponse`.

Ошибки подключения контроллера, недоступный метод и другие реальные сбои `Dispatcher` записывает в `logs/dispatcher-errors.txt`, а пользователю возвращает безопасный `Response` со статусом `500`.

## Page, Response и RedirectResponse

[`Page`](../core/src/Page.php) описывает страницу, которую ещё нужно отрендерить. Она содержит:

- имя макета;
- метаданные;
- имя представления;
- данные представления;
- код HTTP для итоговой страницы.

Например, `ErrorController` возвращает обычную `Page` со статусом `404`, не изменяя глобальный код ответа из контроллера.

[`Response`](../core/src/Response.php) представляет готовый HTTP-ответ: тело, код состояния и набор заголовков. Класс проверяет допустимый диапазон кодов состояния и валидирует заголовки, включая защиту от управляющих символов и дублирования имён без учёта регистра.

[`RedirectResponse`](../core/src/RedirectResponse.php) специализирует `Response` для перенаправления: содержит заголовок `Location`, пустое тело и разрешает коды `301`, `302`, `303`, `307` и `308`.

Поэтому перенаправление, `403 Forbidden` и `405 Method Not Allowed` остаются обычными результатами выполнения метода, а исключения используются только для настоящих ошибок.

## Контроллеры

Базовый [`Controller`](../core/src/Controller.php) помогает создавать `Page` через `render()` и содержит общую работу с пагинацией.

Основной пример находится в [`ArticleController`](../app/Controllers/ArticleController.php):

- `all()` и `show()` возвращают `Page`;
- `create()`, `edit()` и `delete()` возвращают `Page|Response`;
- успешные POST-операции возвращают `RedirectResponse`;
- неверный CSRF-токен возвращает `Response('Forbidden', 403)`;
- попытка удалить статью не методом POST возвращает `405` с заголовком `Allow: POST`;
- отсутствие статьи возвращает `Page` со статусом `404`.

Контроллер не отправляет HTTP-заголовки напрямую и не завершает PHP-процесс через `exit`.

## Модель и PostgreSQL

Базовый [`Model`](../core/src/Model.php) открывает PDO-соединение с PostgreSQL по переменным окружения.

Соединение настроено так:

- ошибки PDO преобразуются в исключения;
- результат по умолчанию возвращается как ассоциативный массив;
- эмуляция подготовленных запросов отключена.

Запросы выполняются через подготовленные выражения PDO. CRUD статей реализован в [`ArticleModal`](../app/Models/ArticleModal.php).

При `PDOException` техническая информация записывается в `logs/database-errors.txt`, после чего выбрасывается `DatabaseException`, сохраняющий исходное исключение. `Dispatcher` знает, что ошибка базы уже записана в журнал, поэтому не делает повторную запись и возвращает пользователю безопасный ответ `500`.

## View и отправка ответа

[`View`](../core/src/View.php) получает `Page`, формирует представление и макет через буферизацию вывода, а затем возвращает готовый `Response`.

Если во время формирования страницы возникает ошибка:

- `View` очищает только те буферы вывода, которые открыл сам;
- техническая причина записывается в журнал;
- пользователю возвращается безопасный ответ `500`.

Обычная отправка HTTP-ответа выполняется только в [`public/index.php`](../public/index.php):

```text
http_response_code()
→ header()
→ echo
```

То есть построение ответа отделено от его фактической отправки клиенту.

## Валидация, CSRF и вывод данных

[`ArticleValidate`](../app/Validations/ArticleValidate.php) проверяет данные статьи на сервере. При ошибке контроллер сохраняет введённые значения и сообщения в сессии, после чего возвращает перенаправление.

[`SecurityHelper`](../app/Helper/SecurityHelper.php) создаёт и проверяет CSRF-токен. Изменяющие операции `create`, `edit` и `delete` выполняют эту проверку до записи в PostgreSQL.

Динамические значения при выводе экранируются. Содержимое статьи хранится как текст: переводы строк преобразуются при отображении, а произвольный HTML пользователя не выполняется.

## Границы ошибок

В проекте разделены штатные HTTP-ответы и реальные ошибки:

```text
перенаправление / 403 / 405
    → обычный Response
    → без записи в журнал ошибок

ошибка PostgreSQL / PDO
    → запись в журнал базы данных
    → DatabaseException
    → безопасный ответ 500

ошибка контроллера или Dispatcher
    → запись в журнал Dispatcher
    → безопасный ответ 500

ошибка представления или макета
    → запись в журнал View
    → безопасный ответ 500
```

Технические сообщения исключений не должны попадать в HTML-ответ пользователю.

## Что сознательно не усложнялось

Проект остаётся небольшим, поэтому в нём нет дополнительных слоёв только ради архитектурной симметрии:

- нет контейнера зависимостей;
- нет ORM;
- нет отдельного слоя репозиториев поверх каждой модели;
- нет цепочки промежуточных обработчиков;
- нет шины событий;
- нет фоновых задач;
- нет отдельного REST API или SPA.

В более крупном прикладном проекте часть этих границ могла бы стать полезной. Здесь они только скрыли бы основной MVC-поток за дополнительной инфраструктурой.

Практические команды запуска, работу с тестовой базой, покрытием и CI см. в [руководстве по разработке](development.md).
